# Инструкция оператора

## Проверить Compose без запуска

Выполнять в WSL из корня репозитория. Нужны Bash, Docker Compose v2
(проверено на v2.35.1) и `jq`. Выберите окружение по [таблице в README](../README.md).

```bash
cd /opt/petar-deploy
bash scripts/check-compose.sh
```

Ожидаются три строки `Compose isolation checks passed`, по одной на окружение.
Скрипт выполняет `docker compose config`: не стартует контейнеры, не скачивает
образы, не создаёт каталоги данных и не запускает runner.

Чтобы вывести итоговый JSON только одного окружения, передайте `--render`
с именем `dev`, `rehearsal` или `production`, например:

```bash
bash scripts/check-compose.sh --render rehearsal |
  jq '{name, networks, services: (.services | map_values({ports, volumes}))}'
```

Сверьте имя проекта, имя сети, порты и источники томов с README. Без фильтра
JSON также содержит **тестовый** пароль и DSN. Скрипт берёт значения из
`env/<окружение>.env.example`, подставляет фиктивные образы/пути релиза и
не использует локальный `.env` или секреты оболочки. Этот результат нельзя
использовать для запуска. Не сохраняйте вывод с реальными секретами в Git.

Если команда не проходит, проверьте, что установлены Compose v2 и `jq` и
запускается именно конфигурация нужного окружения. При расхождении сравните
`compose.yaml`, dev override и выбранный env-пример с таблицей README; не
исправляйте ошибку подключением данных действующей установки.

## Подготовить хост и локальные параметры

Оператор и runner — один непривилегированный пользователь с UID/GID `1000:1000`
(`eam` в шаблоне). Нужны Linux `amd64`, Bash, Python 3.8+, `curl`, `ss`, Docker
Engine без rootless/userns и Compose v2 с `up --wait` (база: v2.35.1).
Для `dev` нужен Git. Docker доступен оператору по `/var/run/docker.sock`
через явный context `default`, с настройками из `~/.docker`. `DOCKER_HOST`,
`COMPOSE_*`, `.env` из репозитория и переменные runner из оболочки не используются.
Закреплённый runner требует именно GNU `timeout`. На Ubuntu, где `timeout`
по умолчанию взят из uutils, обеспечьте доступ к GNU-варианту под именем
`timeout` в указанном ниже `PATH`; наличие одного `gnutimeout` недостаточно.
На файловых системах Docker, каталога оператора и всех целей должно быть
не менее 2 ГиБ свободного места; сборка и фактические данные могут потребовать больше.

Пути, порты и пользователи фиксированы ([таблица](../README.md)). В **выбранном**
окружении заранее подготовьте только родительские каталоги, не данные:

| Каталог | Требование |
|---|---|
| `/opt/petar-data/<env>` | доступен оператору на запись, `0755` |
| `/opt/go-pet/postgres/deploy/<env>` | доступен оператору на запись, `0755`; каталог `data` создаёт команда |
| `/opt/go-pet` | доверенный родитель PostgreSQL, в production также прямой родитель `spool`; checkout нужен только для dev |
| `/opt/petar-data/<env>/operator` | владелец оператор, `0700`; вне Compose mounts |

Предки не должны быть symlink или доступны посторонним для записи, а родители
bind-целей должны быть проходимы для контейнеров. Mount внутри выбранного
дерева, включая подкаталоги spool, запрещён: он мог бы скрыть данные другого
окружения. Preflight также сверяет исходные каталоги чужих bind mounts и
именованных томов. Если оператор не может однозначно разрешить у чужого
mount исходный путь (в том числе из-за прав), проверка останавливается.
При отказе из-за прав на
действующем хосте не меняйте владельцев и режимы его данных; согласуйте отдельный
безопасный стенд или подготовку хоста. Отсутствующие цели создаст команда, а уже
существующие цели должны быть `1000:1000`, `0755`: команды не меняют их права.

В свежем `operator/` создайте ровно один раз пустые `control.lock`, `tick.lock`
и `runner.log`, все `0600`. Не обнуляйте/заменяйте lock-файлы. Создайте там же
`secrets.env` (`0600`, обычный файл без ссылок) с двумя строками:

```text
POSTGRES_PASSWORD=<случайный локальный пароль>
WIKI_CHECK_PASSWORD=<другой случайный локальный пароль>
```

Подставьте разные значения длиной 24–72 символа из `A–Z a–z 0–9 . _ ~ -`.
Комплекты секретов для окружений тоже должны быть разными. Не передавайте
секреты аргументами команд, не копируйте в Git и не меняйте за спиной запущенного
стека. `WIKI_CHECK_PASSWORD` используется для отдельного пользователя `petar_check`
в группе `ai` без прав администратора, а не для веб-установщика. В production
не переиспользуйте пароль или файлы пользователя с репетиции.

## Выполнить команды из корня репозитория

```bash
scripts/preflight.sh dev deploy-001
scripts/dev.sh up
scripts/run-once.sh dev
scripts/dev.sh down

scripts/preflight.sh rehearsal deploy-001
scripts/deploy.sh rehearse deploy-001
```

- `preflight.sh <dev|rehearsal|production> deploy-001` только проверяет условия.
  Для release-профилей проверяет готовность к **чистой** установке, не пытается
  её начать. Рендер сверяется без вывода JSON; Docker только опрашивается, архивы
  проверяются в памяти или в локальном комплекте. `fabric` и `yt-dlp` нужны
  только соответствующим задачам; их наличие сообщается отдельно.
- Перед записью данных команды повторяют проверку после загрузки образов и
  сохраняют проверенный Compose в `operator/runtime.compose.json` (`0600`).
  Это рабочий файл с паролем/DSN, не отчёт: не редактируйте и не публикуйте его.
  Запуск и остановка используют этот Compose, а не повторно читают исходный YAML.
- `dev.sh up` собирает API из текущих `Dockerfile`, `go.mod`, `go.sum`, `cmd/`,
  `internal/` в `/opt/go-pet`. Сборщик получает снимок только этих файлов
  (не `.git`, spool или данные БД). Локальные файлы вне этих границ, включая
  исключённые Git, в сборку не входят. PG берёт файлы из Go checkout,
  плагин монтируется read-only из `/opt/php-wiki-plugin`. Не заменяйте эту
  команду прямым `docker compose ... build` с корнем Go checkout.
- `dev.sh down` останавливает только подтверждённый dev-проект без `-v` и
  оставляет данные, даже если исходный YAML или файлы сборки в checkout сломаны.
  Последующий `up` снимает штатную пометку останова; аварийную паузу он не снимает.
- `deploy.sh rehearse deploy-001` и `deploy.sh init deploy-001` выбирают
  соответственно rehearsal и production. `init` **не** запускайте на рабочем
  хосте до отдельного разрешения cutover. Любой непустой PG18 bind-родитель,
  wiki или spool, включая скрытый файл в старом spool, означает отказ.
  Пины и OCI revision проверяются до запуска; готовый комплект публикуется
  в `operator/deploy-001/`. Штатные плагины, ACL и запрет `install.php`
  подготавливаются до публикации HTTP. После старта проверяется не только запись
  о миграции `000008` в логе, но и её эффект: старой SQL-функции ввода больше нет.
  API ждёт TCP PostgreSQL, а не временный Unix-сокет bootstrap; Docker даёт
  bootstrap 90 секунд до учёта неудачных проб.
  Успех означает «подготовлено,
  ожидает smoke», а не «развёрнуто»; задания не отправляются.
- `deploy.sh upgrade deploy-001` всегда сообщает, что обновление не
  поддерживается, и завершается без изменений.

## Runner, журнал и восстановление

Единственный операторский вход — `scripts/run-once.sh <dev|rehearsal|production>`.
Он выбирает соответствующий runner, `HOME`, `PATH`, spool и callback; не
запускайте оригинальный runner напрямую (у него рабочие значения по умолчанию).
`HOME` берётся из системной записи пользователя, `PATH` — фиксированные
системные каталоги, затем `~/.local/bin` и `~/go/bin`. Перед проходом проверяются
свой Compose-проект и readiness API. При занятом lock или обслуживании тик
пропускается. Непустой `processing`, незавершённый `inflight` либо ненулевой
код runner требуют сверки с БД; wrapper не повторяет callback и не меняет job-файлы.
Перед запуском wrapper проверяет только метаданные входных и выходных файлов.
Symlink, hardlink, FIFO и недоверенные права означают отказ и паузу; содержимое
таких файлов не читается.

Операция обслуживания берёт `control.lock`, сохраняет `maintenance`,
затем до 120 секунд ждёт `tick.lock`. Пока активный runner не выйдет,
его API остаётся доступен. Runner держит `tick.lock` весь проход и передаёт
его дочернему процессу. Внутренний `.runner.lock` принадлежит самому runner;
эти lock-файлы нельзя удалять, заменять или использовать для ротации.

При отказе ориентируйтесь на стадию диагностики. Не публикуйте сырой вывод
Compose, Docker inspect, журналов приложений или файлы очереди. Если отказ
возник после `maintenance`, подготовка может быть частичной, а уже запущенные
сервисы останутся работать для диагностики. Не повторяйте `init` и не очищайте
данные автоматически. В одноразовой VM безопаснее пересоздать стенд; рабочие
данные восстанавливаются только по отдельному согласованному плану.

После устранения причины подтвердите окружение, состояние контейнеров и
записи БД для каждого остатка `processing`. Оператор выполняет сверку
и снимает только проверенные флаги в одной сессии под обеими блокировками,
в том же порядке, например для dev:

```bash
(
  set -e
  cd /opt/petar-data/dev/operator
  exec 8<>control.lock 9<>tick.lock
  flock -w 120 8
  flock -w 120 9
  # Здесь оператор выполняет сверку и только после этого снимает проверенные флаги.
)
```

Не снимайте `maintenance`, чтобы запустить runner поверх частичной установки.
Не снимайте `pause`/`inflight` до сверки; само удаление флага не исправляет БД.

[`templates/petar-runner.cron`](../templates/petar-runner.cron) и
[`templates/petar-runner.logrotate`](../templates/petar-runner.logrotate) —
образцы для последующего согласованного включения. `runner.log` принадлежит
`eam:eam`, `0600`, и содержит только stdout/stderr wrapper, не сырой вывод
runner с идентификаторами и возможными данными задания. Ротация не
включает расписание; эти команды не пишут в `/etc`.

## Приёмка DEPLOY-06

`bash scripts/test-deploy.sh contracts` использует временное дерево и заглушки,
за исключением локального `docker compose config`, который не подключается к daemon.
`bash scripts/test-deploy.sh isolated` запускайте **только** в заново созданной
Linux VM, не в WSL/контейнере и не с примонтированными рабочими каталогами или
сокетом. На ней нужен отдельный daemon без контейнеров, доступ к registry и
GitHub, свободные порты всех трёх профилей. Деревья проекта и Docker должны
располагаться на гостевых ext4/xfs без вложенных mounts; Unix-сокет
`/run/docker.sock` открывает непосредственно гостевой `dockerd` (без
пересылки или systemd socket activation). Тест сверяет PID владельца сокета,
имя хоста, ядро и точки монтирования, видимые демону. Администратор VM подтверждает,
что её можно целиком уничтожить: создаёт root-owned файл
`/etc/petar-deploy-disposable` с её собственным `/etc/machine-id`, без прав
записи для группы/остальных. Не создавайте этот файл на рабочем хосте.

Подготовьте только указанные выше родители и три пустых `operator/`, плюс
пустой `/opt/php-wiki-plugin` владельца UID/GID `1000:1000`. Не создавайте
секреты, данные или checkout приложений: тест подготовит свои секреты и
подключит исходники только после обеих release-установок. Запускать от UID/GID
`1000:1000` из отдельной deploy-копии в VM. При успехе тест остановит только свои
проекты; при отказе сохранит их для диагностики. Не используйте VM повторно
без её пересоздания. Код `77` означает, что изоляция не подтверждена и мутации
не начались: это блокер приёмки, а не успешная проверка.

## Сквозная проверка DEPLOY-07

Запускайте из корня deploy-копии под UID/GID `1000:1000` на хосте
уже подготовленного `deploy-001`. Smoke проверяет профиль, frozen Compose,
контейнеры, отсутствие обслуживания/паузы, readiness и точный каталог действий.
Вход выполняется в настоящем Chromium под `petar_check`, с паролем из
приватной конфигурации выбранного профиля. **Это не read-only probe**: каждый
запуск отправляет `echo-test` с новым маркером и `word-count` с тремя словами.
Обе задачи остаются в журнале. `fabric` и `yt-dlp` не исполняются.
Чистые `rehearse` и `init` создают пустые `in/`, `processing/`, `out/` в
выбранном spool до запуска Go: bind mount скрывает каталоги из образа.

```bash
bash scripts/smoke.sh rehearsal deploy-001
bash scripts/smoke.sh rehearsal deploy-001 --scheduled
bash scripts/smoke.sh production deploy-001
```

- **Rehearsal без флага:** выделите стек и окно только для smoke. Выключите
  внешние тики этого профиля, исключите другие вызовы runner и отправки заданий
  через API/wiki на время проверки. Очередь должна быть пустой, включая ранее
  принятые, но ещё не выгруженные в spool задания. Только после этого создайте
  от имени оператора приватный файл с точным содержимым:

  ```bash
  (
    umask 077; set -C
    printf '%s\n' 'dedicated rehearsal runner' > /opt/petar-data/rehearsal/operator/smoke-managed
  )
  ```

  Файл — явное подтверждение выделенного стенда, не средство остановки других
  исполнителей. Перед штатным `run-once.sh rehearsal` smoke сверяет имена
  входных файлов с двумя ID журнала, не читая payload. Другие режимы этому файлу
  не доверяют и runner не запускают.
- **Rehearsal с `--scheduled`:** нужен уже работающий внешний runner
  этого профиля. Установка расписания не входит в процедуру. Как и в ручной
  репетиции, после сверки результатов перезапускаются `postgres`, `app` и
  `dokuwiki` под обычными блокировками обслуживания, с сохранением bind-данных.
  Smoke проверяет смену `StartedAt` у всех трёх и заново входит в wiki из
  отдельного браузерного контекста. Выбирайте окно, допускающее перерыв.
- **Production:** только ожидает штатного runner и проверяет две публикации,
  без тика, обслуживания или перезапуска. Используйте только после отдельно
  согласованной установки; не запускайте на старом рабочем стеке.

Для внешнего runner ожидание журнала ограничено 150 секундами (включая
ожидание следующей минуты). Просмотр ограничен 25 страницами журнала на одну
сверку. Код `0` означает, что найдены собственные `input_id/process_id/job_id`,
обе строки `completed`, обе карточки `job_result` ответили `200` с точными
типами, версиями и значениями. Для rehearsal всё повторно прочитано по тем же
ID без новых submit. Результат относится только к этому запуску, не меняет
маркер «подготовлено, ожидает smoke» и не подтверждает сторонние интеграции.

При ненулевом коде смотрите профиль, стадию, известные ID и последний статус.
Если submit прервался, результат создания может быть неизвестен: запрос не
повторяется. Сначала сверьте журнал `petar_check` и очередь; не очищайте данные
и не снимайте паузу, `inflight` или оставшийся после сбоя рестарта `maintenance`
без [сверки](#runner-журнал-и-восстановление). Не пересылайте сырой Docker-вывод,
токены, cookie или пароль. Браузерная сессия временная, без trace или
постоянного профиля.

### Браузер и одноразовая VM

Используется root-owned `/opt/petar-smoke`, Playwright `1.60.0`, Chromium
Headless Shell `148.0.7778.96` для Linux amd64. Зависимости закреплены
[хешами колёс](../scripts/smoke-requirements.txt) и SHA-256 архива в
[Ansible-рецепте](../scripts/provision-smoke-vm.yml). Smoke требует включённую
песочницу Chromium и отказывает до отправки, если браузер не запускается.
Артефакты устанавливаются заранее, а не при каждом smoke; checkout Go/PHP
не требуется. На рабочий хост не переносите VM-playbook.

На подтверждённой одноразовой Ubuntu 26.04 amd64 с UID/GID `1000:1000`,
Ansible и `sudo` подготовьте гостя. Скопируйте playbook и файл зависимостей
в один временный каталог **на VM**, затем оттуда:

```bash
ansible-playbook provision-smoke-vm.yml -e confirmed_disposable=yes
```

Рецепт создаёт только родителей тестовых путей, устанавливает браузер,
гостевой Docker с прямым Unix-сокетом и GNU `timeout`, выпускает аттестацию.
На свежем госте он отказывает при следах прежнего Docker/containerd и
использует собственный `/var/lib/petar-acceptance-docker`.
При смене группы Docker заново войдите на VM. Передайте точное дерево deploy
в `/opt/petar-deploy` без локальной конфигурации или данных приложений. На
переиспользуемом госте подготовка допустима только после сверки аттестации,
локальности daemon и принадлежности каждого прежнего тестового дерева;
отложите их отдельно, не удаляя `/opt` целиком. Только после сверки на
таком госте используйте `-e reuse_attested=yes`. При сомнении используйте
новую VM.

```bash
cd /opt/petar-deploy
bash scripts/test-smoke.sh isolated
```

Harness сначала проверяет аттестацию DEPLOY-06, пустые тестовые пути и
локальный daemon без чужих сетей, томов или контейнеров, затем создаёт
тестовые секреты, выполняет публичные `preflight.sh`, `deploy.sh rehearse` и
`smoke.sh`. Он останавливает только проверенный тестовый Compose-проект,
проверяет отсутствие его контейнеров и сети и сохраняет данные на госте.
Код `77` — стенд не подтверждён, а не успешная приёмка.
`bash scripts/test-smoke.sh contracts` можно запустить локально без стека
и браузера; заглушки в контрактах не заменяют реальный `isolated`.
